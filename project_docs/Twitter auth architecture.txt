System ko securely identify karna hai ki:

5. Why bcrypt?

Password ko simple hash se store karna enough nahi hai.

bcrypt specifically password hashing ke liye designed hai.

Example concept:

"mypassword"
      ↓
    bcrypt
      ↓
"$2b$10$..."

Same password ka hash bhi different salt ki wajah se different ho sakta hai.

Backend password ko decrypt nahi karta.

Instead:

Login password
      ↓
bcrypt.compare()
      ↓
matches?

7. JWT Architecture

Hum JWT-based authentication use karenge for our custom email/password authentication.

JWT = JSON Web Token.

Concept:

      ↓

      ↓

8. Access Token

Access token short-lived hoga.

Example conceptual lifetime:

15 minutes

Request:

Authorization: Bearer <access-token>

Backend:

Verify JWT
   ↓
Extract user identity
   ↓
req.user

Example payload conceptually:

{
  "sub": "user_id",
  "type": "access",
  "iat": 1750000000,
  "exp": 1750000900
}

sub = user identity.

9. Refresh Token

Access token short-lived hai, toh user ko har 15 minutes login nahi karwana.

Isliye:

Access Token
+
Refresh Token

Flow:

Access token expired
        ↓
Refresh token
        ↓
POST /api/v1/auth/refresh
        ↓
Server validates refresh token
        ↓
New access token

Refresh token longer-lived hoga.

Example:

7 days

Exact expiry implementation phase mein configuration se finalize karenge.

10. Token Storage

Security ke liye browser mein authentication tokens ko casually:

localStorage

mein store nahi karenge.

Preferred architecture:

Access Token
→ short-lived

Refresh Token
→ HttpOnly + Secure Cookie

HttpOnly ka matlab JavaScript directly cookie read nahi kar sakta.

Secure ka matlab cookie HTTPS connection par hi send hogi.

Development aur production environment ke according cookie settings configure hongi.

14. Authorization Architecture

Authentication ke baad authorization.

Example:

User A
 ↓
DELETE /api/v1/posts/123
 ↓
Authenticated? YES
 ↓
Post exists? YES
 ↓
post.author == User A?
 ↓
YES → allow

Agar User B try kare:

Authenticated? YES
Post exists? YES
Owner? NO
      ↓
403 Forbidden

17. Authentication vs Authorization

Isko strongly remember kar:

AUTHENTICATION
"Who are you?"
       ↓
Firebase / Password + JWT
AUTHORIZATION
"What are you allowed to do?"
       ↓
Ownership / Roles / Permissions

Example:

Rajat logged in
       ↓
Authentication ✅
       ↓
Delete John's post
       ↓
Authorization ❌
       ↓
403

27. Architecture Decision

Final decision:

Email/Password authentication will be implemented through our Express backend so that authentication fundamentals are learned practically. Google Sign-In will use Firebase Authentication for identity verification. Express will remain the application's security boundary and will perform authentication verification and authorization for protected resources.

Iska matlab Firebase hamare backend ko replace nahi karega.

Firebase
→ Google identity

Our Backend
→ Application authentication
→ Authorization
→ Business rules
→ Users
→ Posts
→ Permissions
